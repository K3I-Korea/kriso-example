# 00. 무엇을 다루는가, 그리고 바로 돌려 보기

2강은 **상태(state)**를 다룬다. 스위치가 켜졌는지, 입력이 틀렸는지, 지금 적용 중인지 같은 "지금 어떤 상태인가" 를 React·Lit(웹 컴포넌트)·Figma 세 곳에서 **어긋나지 않게** 잇는 것이 목표다. 이 장을 끝내면 상태 실습 화면이 손에서 돌아가고, 다음 장부터 그 구조를 하나씩 뜯어본다.

## 0-1. 2강이 1강과 다른 점

1강은 "디자인 값(토큰)과 컴포넌트를 한 번만 만들어 여러 곳에서 쓴다" 였다. 2강은 그 컴포넌트가 **상태를 가질 때** 생기는 문제를 다룬다.

- 상태는 세 곳에 서로 다른 이름으로 나타난다: Figma 의 variant, Lit 의 속성, React 의 state.
- 그 상태를 누가 소유하고, 거부(예: 잠금 중 변경 막기)는 어떻게 하고, 바깥에 노출할 상태와 감출 상태를 어떻게 가르는지를 본다.

프로젝트는 1강과 **같은 `k3i-ds`** 다. 1강에서 만든 토큰과 컴포넌트는 그대로 쓰고, 2강은 `ds-switch` 컴포넌트와 상태 실습 화면(`demo/react.html`)을 더한다.

### 먼저 알아 둘 말

- **상태(state)**: "지금 어떤 모습인가" 를 나타내는 값. 켜짐/꺼짐, 정상/오류, 적용 중 같은 것.
- **반응형 속성(reactive property)**: 값이 바뀌면 컴포넌트가 화면을 자동으로 다시 그리는 속성. Lit 의 `@property`·`@state` 가 그렇다.
- **reflect**: Lit 속성 값을 HTML 속성으로 내보내는 설정. 켜면 `<ds-switch checked>` 처럼 DOM 에 드러나고, CSS 와 Figma variant 가 그 값을 볼 수 있다.
- **단일 진실 공급원(single source of truth)**: 같은 값을 여러 곳이 각자 들고 있지 않고, **한 곳에서만** 정해 나머지가 따라오게 하는 것. 이 실습에서는 React 가 상태의 단일 공급원이다.
- **취소 가능한 이벤트(cancelable event)**: 받는 쪽이 `preventDefault()` 로 "거부" 할 수 있는 이벤트. 거부하면 보낸 쪽이 동작을 되돌린다.

## 0-3. 설치하고 실습 화면 띄우기

`k3i-ds` 폴더로 들어가 설치한 뒤 개발 서버를 띄운다.

```bash
cd k3i-ds
npm install        # 처음 한 번만
npm run dev
```

브라우저에서 **http://localhost:5173/demo/react.html** 을 연다. `상태 실습 — React × Lit × Figma` 화면이 나오면 성공이다.

> 1강 데모(루트 `index.html`)는 `http://localhost:5173` 이고, 2강 상태 실습은 `http://localhost:5173/demo/react.html` 이다. 주소 끝이 다르다.

## 0-4. 화면에서 볼 것

화면은 왼쪽 **조작 패널**과 오른쪽 **관찰 패널**로 나뉜다.

### ① 왼쪽을 조작하면 오른쪽이 실시간으로 바뀐다

왼쪽에서 자율운항 스위치를 켜고 속력을 입력해 본다. 오른쪽 **②③ 표**에 그 조작이 만든 **DOM 속성**과, 그에 대응되는 **Figma variant** 가 바로바로 바뀐다. 같은 상태가 세 가지 이름으로 동시에 보이는 것이다.

### ② 원격 잠금으로 "거부" 를 본다

1. **원격 잠금** 스위치를 켠다.
2. 그 상태에서 **자율운항 모드** 스위치를 눌러 본다.
3. 스위치가 잠깐 켜졌다가 **원래대로 돌아간다.** 오른쪽 ④ 로그에 "잠금 상태라 React 가 거부" 가 뜬다.

왜 그런가. 스위치(Lit)가 먼저 낙관적으로 켜고 `ds-change` 이벤트를 보내면, React 가 잠금 중이라 `preventDefault()` 로 거부하고, 그러면 Lit 이 값을 되돌린다. 이 과정은 02·03장에서 코드로 본다.

### ③ 누르는 동안 thumb 이 늘어난다 — 그런데 표엔 안 나온다

자율운항 스위치를 **누르고 있는 동안** 동그라미(thumb)가 살짝 늘어난다. 이것은 `pressed` 라는 **내부 전용 상태**다. 그런데 오른쪽 **② DOM 속성 표에는 나타나지 않는다.** 내부 상태는 DOM 속성으로 노출되지 않기 때문이다. 이 차이가 2강의 핵심 하나다(02장).

## 0-5. 이번에 자주 열 파일

| 파일 | 무엇인가 |
|---|---|
| `src/components/ds-switch.ts` | 상태 세 종류를 보여 주는 스위치 컴포넌트 |
| `demo/state-lab.tsx` | 상태 실습 화면(React 가 상태 소유) |
| `demo/react.html` | 그 화면을 띄우는 HTML |
| `src/react/index.ts` | `@lit/react` 래퍼(`Switch` 등) |
| `figma/code-connect/ds-switch.figma.ts` | `pressed` 를 매핑하지 않는 이유 (05장) |

> **📦 "상태 관리" 라고 하면 Redux 같은 게 아니라?**
>
> 여기서 말하는 상태 관리는 Redux·Zustand 같은 **상태 관리 라이브러리**가 아니다. 이 실습은 React 기본 기능인 `useState` 하나만 쓴다(`state-lab.tsx`). 2강이 다루는 것은 "어떤 라이브러리로 상태를 담느냐" 가 아니라, **컴포넌트(Lit)와 앱(React)과 디자인(Figma) 사이에서 상태를 누가 쥐고 어떻게 주고받느냐** 다. 라이브러리를 더 써도 이 구조는 그대로다.

> **📦 React 가 아니라면? — 상태를 Lit 컴포넌트 안에 두면**
>
> 스위치가 자기 상태를 스스로 쥐게 만들 수도 있다(`<ds-switch>` 가 눌리면 알아서 켜짐). 간단한 화면이면 그게 편하다. 하지만 "잠금 중이면 켜지 못하게" 처럼 **앱의 다른 값에 따라 막아야** 하면, 스위치만으로는 판단할 수 없다. 그래서 이 실습은 상태를 **React 가 소유**하고, 스위치는 "눌렸다" 만 알리고 켤지 말지는 React 가 정하게 한다. 소유자를 하나로 두는 것이 핵심이다(03장).

## 이 장에서 한 것

- 2강이 다루는 것이 "상태를 세 곳에서 어긋나지 않게 잇기" 임을 봤다.
- `npm run dev` 로 상태 실습 화면(`demo/react.html`)을 띄웠다.
- 조작 ↔ 관찰, 잠금으로 거부, 누르는 동안 pressed(표엔 안 나옴)를 눈으로 봤다.

다음 **01장**에서는 같은 상태가 Figma·Lit·React 세 층에서 어떻게 이어지는지를 그림으로 정리한다.
