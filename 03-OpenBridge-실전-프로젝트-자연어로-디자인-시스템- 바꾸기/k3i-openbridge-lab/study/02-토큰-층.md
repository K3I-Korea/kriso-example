# 02. 토큰 층 — 색은 OpenBridge 변수를 가리킨다

가장 아래 Token 층부터 본다. 1·2강의 토큰은 색 값(`#3b5bdb`)을 직접 담았지만, 이 프로젝트의 토큰은 대부분 **OpenBridge 변수를 가리킨다.** 그래서 밝기 팔레트를 바꾸면 K3I 색이 자동으로 따라온다.

## 2-1. `design/tokens.json` — 가리키거나, 값을 담거나

`design/tokens.json` 을 연다. 토큰마다 두 가지 중 하나다.

```json
"color": {
  "surface": { "ob": "--container-background-color" },   // OpenBridge 변수를 가리킴 (권장)
  "alarm":   { "ob": "--alert-alarm-color" },
  ...
},
"space": {
  "4": { "value": "16px" }                               // OpenBridge 에 없는 값은 직접 담음
}
```

- **`{ "ob": "--..." }`** — OpenBridge 가 정의한 변수를 가리킨다(alias). 색은 대부분 이 방식이다. OpenBridge 가 팔레트(밝기)에 따라 그 변수 값을 바꾸므로, K3I 토큰도 자동으로 따라온다.
- **`{ "value": "16px" }`** — OpenBridge 에 대응 변수가 없을 때만 값을 직접 담는다(간격·테두리 두께 등).

색을 직접 `#hex` 로 적는 것은 OpenBridge 에 맞는 변수가 없을 때만 허용한다. 예로 `manual`(수동) 색은 전용 변수가 없어 강조색(`--element-active-enhanced-color`)을 대신 가리킨다(파일의 `$description` 에 그 사정이 적혀 있다).

## 2-2. `npm run tokens` — JSON 을 CSS 변수로

```bash
npm run tokens
```

이 명령은 `scripts/build-tokens.mjs` 를 돌려 `design/tokens.json` 을 `src/styles/k3i-tokens.css` 로 바꾼다. 하는 일은 셋이다.

1. 토큰 이름을 `--k3i-{그룹}-{이름}` 으로 만든다. 예: `color.surface` → `--k3i-color-surface`.
2. `{ "ob": "--x" }` 는 `--k3i-...: var(--x);` 로, `{ "value": "16px" }` 는 `--k3i-...: 16px;` 로 낸다.
3. 가리키는 OpenBridge 변수가 **실제로 있는지 검사한다**(OpenBridge 의 `openbridge.css` 에서 찾는다). 오타나 버전 변경으로 없는 변수를 가리키면 오류를 내고 멈춘다.

결과 `src/styles/k3i-tokens.css` 는 이렇게 생겼다.

```css
:root {
  --k3i-color-surface: var(--container-background-color);
  --k3i-color-alarm:   var(--alert-alarm-color);
  --k3i-space-4: 16px;
  ...
}
```

**확인**: `npm run tokens` 뒤 `src/styles/k3i-tokens.css` 를 열어, `--k3i-color-alarm` 이 `var(--alert-alarm-color)` 를 가리키는지 본다. 패널 코드는 `#hex` 가 아니라 `var(--k3i-color-alarm)` 만 쓴다.

## 2-3. 팔레트 — 밝기를 바꾸면 색이 따라온다

OpenBridge 는 밝기 팔레트 네 가지(bright·day·dusk·night)를 가진다. 팔레트를 바꾸면 OpenBridge 는 `[data-obc-theme="night"]` 같은 선택자로 자기 변수 값을 바꾼다. K3I 토큰이 그 변수를 **가리키고만** 있으므로, 따로 손대지 않아도 K3I 색이 함께 바뀐다(00장의 밝기 버튼이 그것이다).

필요하면 K3I 가 팔레트별로 색을 직접 덮어쓸 수도 있다. `tokens.json` 의 토큰에 `palettes` 를 두면, 빌드가 `:root[data-obc-theme="night"] { ... }` 블록에 그 색만 따로 낸다. 지금 기본 토큰에는 덮어쓰기가 없어 OpenBridge 를 그대로 따라간다.

> **📦 OpenBridge 변수 대신 `#hex` 를 직접 쓰면?**
>
> 색을 토큰에 `#3b5bdb` 처럼 박으면, 밝기 팔레트를 바꿔도 그 색은 안 바뀐다. 야간에도 주간 색 그대로라 시인성이 틀어진다. OpenBridge 변수를 가리키면 팔레트가 색을 책임지므로, K3I 는 "어떤 쓰임에 어떤 OpenBridge 색을 쓸지" 만 정하면 된다. 그래서 `#hex` 직접 입력은 대응 변수가 정말 없을 때만 쓰고, 그때도 `$description` 에 까닭을 적는다.

> **📦 빌드가 "OpenBridge 변수 존재 검사" 를 왜 하나?**
>
> `tokens.json` 에서 변수 이름을 한 글자 틀리게 적거나, OpenBridge 버전이 올라가며 변수 이름이 바뀌면, 그 토큰은 **아무 색도 못 가리킨다.** 화면에서는 조용히 색이 빠질 뿐 오류가 안 보여 찾기 어렵다. 그래서 `build-tokens.mjs` 는 가리키는 변수가 OpenBridge 의 CSS 에 실제로 있는지 빌드 때 검사해, 없으면 그 자리에서 멈춘다. 틀린 참조가 화면까지 가지 못하게 막는 장치다.

## 이 장에서 한 것

- `tokens.json` 이 OpenBridge 변수를 가리키거나(`ob`) 값을 직접 담는(`value`) 두 방식을 봤다.
- `npm run tokens` 가 `--k3i-*` CSS 변수를 만들고 OpenBridge 참조를 검사하는 것을 봤다.
- 밝기 팔레트를 바꾸면 K3I 색이 자동으로 따라오는 까닭을 봤다.

다음 **03장**에서는 그 토큰을 쓰는 "상태" 를 본다. 값 하나가 가질 수 있는 6종 상태를 누가 결정하는지 다룬다.
