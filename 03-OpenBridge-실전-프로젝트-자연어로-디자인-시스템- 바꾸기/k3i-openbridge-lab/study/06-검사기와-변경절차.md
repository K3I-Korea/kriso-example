# 06. 검사기와 변경 절차

자연어로 선언(JSON)을 고치면, 그 변경이 서로 아귀가 맞는지 **검사기**가 확인한다. 검사를 통과하지 못하면 화면에 반영되지 않게 하는 안전장치다. 이 장에서는 `npm run check` 가 무엇을 보는지와, 변경을 끝까지 흘려보내는 절차를 본다.

## 6-1. `npm run check` — 선언끼리 아귀가 맞는지 본다

```bash
npm run check
```

`scripts/validate.mjs` 가 `design/` 의 선언 파일 전체를 맞대어 본다. 보는 것:

| 대상 | 무엇을 확인하나 |
|---|---|
| tokens | 색 토큰이 OpenBridge 변수(또는 팔레트 덮어쓰기)로 풀리는지 |
| states | 상태 6종(normal·degraded·stale·invalid·alarm·manual)이 다 있는지, `priority` 의 끝이 `normal` 인지, 각 `token` 이 `tokens.json` 색에 있는지, `shape` 가 지원되는 6종인지 |
| signals | 필수 항목(topic·label·unit·ttlMs …)이 있는지, `topic` 이 겹치지 않는지, 임계값(`limits`)이 오름차순·`limitsBelow` 가 내림차순인지 |
| layouts | `areas` 의 칸 수가 `columns` 와 맞는지, 줄 수가 `rows` 와 맞는지 |
| views | `layout` 이 있는지, 슬롯이 그 레이아웃에 있는지, `panel` 이 `panels.json` 에 있는지, 패널의 `roles` 가 모두 연결됐고 그 신호가 `signals.json` 에 있는지 |

틀린 데가 있으면 멈추고(종료 코드 1), **무엇을 어떻게 고치면 되는지**가 드러나게 메시지를 낸다. 예:

```
✖ 디자인 선언 검사 실패 (1건)
  [views/overview.json] 슬롯 "kpi9" 은 l1-grid 에 없습니다 (가능: primary, secondary, tertiary, kpi-1, kpi-2, kpi-3)
```

이렇게 "가능한 값" 까지 함께 알려 주므로, 사람도 Claude 도 그 메시지만 보고 바로잡을 수 있다. 통과하면 이렇게 나온다.

```
✔ 디자인 선언 검사 통과 — 신호 7 · 패널 3 · 레이아웃 2
```

`npm run check` 는 `npm run dev` 와 `npm run build` 앞에서 **자동으로 먼저 돈다**(`package.json` 의 `predev`·`prebuild`). 그래서 검사를 통과하지 못한 선언으로는 화면이 뜨지 않는다.

## 6-2. OpenBridge 변수 찾아보기 — `npm run ob:vars`

색 토큰을 OpenBridge 변수에 연결할 때, 어떤 변수가 있는지 찾아보는 학습용 스크립트다.

```bash
npm run ob:vars                 # 접두어별 변수 개수 요약
npm run ob:vars -- alert-caution   # "--alert-caution" 으로 시작하는 변수의 네 팔레트(bright·day·dusk·night) 값 비교표
```

예를 들어 "야간에 주의색을 덜 눈에 띄게" 같은 요청이면, `-- alert-caution` 과 `-- alert-warning` 을 비교해 어떤 변수를 쓸지 고른 뒤 `tokens.json` 에 반영한다.

## 6-3. 변경 절차 (CLAUDE.md 2절, 반드시 이 순서)

1. 요청을 6계층 표로 분류하고, **어떤 파일의 어떤 키를 바꿀지 먼저 한 줄로 말한다.**
2. `design/` JSON 을 고친다(코드보다 선언 우선).
3. `npm run check` — 틀리면 메시지대로 고치고 다시 돌린다(통과할 때까지).
4. 토큰을 건드렸다면 `npm run tokens`.
5. `npm run typecheck`.
6. `npm run dev` 상태에서 해당 화면을 확인한다(가능하면 주간·야간 둘 다 스크린샷).
7. Figma 동기화(연결돼 있으면, 07장).
8. 무엇을 바꿨는지 파일·키 단위로 요약한다.

> **📦 검사기가 없으면?**
>
> 자연어로 JSON 을 고치다 보면 슬롯 이름을 잘못 쓰거나, 없는 신호를 연결하거나, 임계값 순서를 뒤집기 쉽다. 검사기가 없으면 이런 실수가 그대로 화면으로 넘어가 엉뚱하게 그려지거나 빈 칸이 생긴다. `npm run check` 는 선언끼리 아귀가 맞는지를 **미리** 보고, 틀리면 막으면서 고칠 말을 알려 준다. 그래서 "자연어 변경 = JSON 편집" 이 안전해진다. 이 검사가 `predev` 로 먼저 도니, 통과 못 한 선언으로는 화면이 아예 안 뜬다.

> **📦 통과(0건)가 나오면 그걸로 끝인가?**
>
> 아니다. 검사기는 **선언의 일관성**만 본다 — 슬롯 이름이 맞는지, 상태 6종이 다 있는지, 임계 순서가 맞는지. 화면이 실제로 **읽히는지**(글자가 보이는지, 야간에 대비가 충분한지), 바꾼 내용이 **규정에 맞는지**(경보 색·깜빡임 규칙 등)는 검사기가 모른다. 그래서 통과한 뒤에도 주간·야간 두 팔레트로 눈으로 확인하는 6-3 의 6단계를 생략하지 않는다. "0건 통과" 는 "검사기가 보는 것만 맞다" 는 뜻이지 "다 맞다" 는 뜻이 아니다.

## 따라 하기

1. `npm run check` 를 돌려 통과 메시지를 본다.
2. `design/views/overview.json` 의 어느 슬롯 이름을 일부러 틀리게(`kpi-1` → `kpi9`) 바꿔 저장하고 다시 `npm run check` 를 돌린다. 어떤 메시지로 막는지 본다. 확인했으면 되돌린다.
3. `npm run ob:vars -- container` 로 OpenBridge 변수의 네 팔레트 값이 어떻게 다른지 본다.

## 이 장에서 한 것

- `npm run check` 가 tokens·states·signals·layouts·views 의 아귀를 맞대어 보고, 틀리면 고칠 말과 함께 막는 것을 봤다.
- `npm run ob:vars` 로 OpenBridge 변수를 찾아보는 방법을 봤다.
- 변경을 끝까지 흘려보내는 8단계 절차를 봤다.
- "0건 통과" 가 전부가 아니라, 눈으로 확인하는 단계가 남는다는 것을 봤다.

다음 **07장**에서는 이 모든 것을 묶어, 자연어 요청이 실제로 어느 파일로 흘러가는지와 Figma 동기화를 다룬다.
