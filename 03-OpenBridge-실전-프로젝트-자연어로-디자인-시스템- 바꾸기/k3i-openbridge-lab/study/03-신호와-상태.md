# 03. 신호와 상태 — 값 하나가 가질 수 있는 6종

대시보드의 수치는 그냥 숫자가 아니다. 갱신이 끊겼는지, 경보에 걸렸는지, 수동 보정 중인지에 따라 색·형태·문구가 달라진다. 이 장은 신호(값)와 상태(그 값의 처지)를 본다.

## 3-1. `design/signals.json` — 신호 카탈로그

`design/signals.json` 을 연다. 화면에 올릴 값마다 토픽·단위·자릿수·수명(ttl)·임계값을 적어 둔다.

```json
"exhaust": {
  "topic": "vessel/engine/me1/exhaust-temp", "label": "EXH. TEMP", "unit": "°C",
  "fractionDigits": 0, "maxDigits": 3, "ttlMs": 3000,
  "limits": { "caution": 400, "warning": 420, "alarm": 440 }
},
"lube": {
  "topic": "vessel/engine/me1/lube-press", "label": "LUBE OIL", "unit": "bar",
  "ttlMs": 3000, "limitsBelow": { "warning": 2.5, "alarm": 2.0 }
}
```

- `ttlMs` — 이 시간(밀리초)을 넘도록 새 값이 안 오면 **갱신 없음(stale)** 으로 본다.
- `limits` — 값이 이 수치를 **넘으면** 경보 수준(caution·warning·alarm)에 든다. 배기온도가 440 을 넘으면 alarm.
- `limitsBelow` — 값이 이 수치 **아래로** 내려가면 경보에 든다. 윤활유 압력이 2.0 밑이면 alarm.

"배기온도 경보를 440도로" 같은 요청은 여기 `limits.alarm` 을 고쳐 끝난다(01장의 데이터 층).

> 신호 토픽·임계값은 실습용 가정값이다. 실제 과제에서는 과제의 신호 카탈로그로 교체한다(`signals.json` 의 `$description`).

## 3-2. `design/states.json` — 상태 6종과 우선순위

값 하나가 가질 수 있는 상태는 여섯이다. 상태마다 **색 토큰 + 형태 + 문구** 를 정하고, 여러 상태가 동시에 성립하면 **우선순위로 하나만** 보여 준다.

```json
"priority": ["invalid", "alarm", "stale", "degraded", "manual", "normal"],
"states": {
  "normal":   { "token": "text",    "shape": "none",         "text": "" },
  "degraded": { "token": "caution", "shape": "dashed-border", "text": "품질 저하" },
  "stale":    { "token": "caution", "shape": "dim-value",    "text": "갱신 없음 {age}s" },
  "invalid":  { "token": "alarm",   "shape": "hide-scale",   "text": "신호 없음" },
  "alarm":    { "token": "alarm",   "shape": "strong-border", "text": "{reason}" },
  "manual":   { "token": "manual",  "shape": "left-bar",     "text": "수동" }
}
```

- `token` — 02장의 색 토큰 이름(예: `alarm` → `--k3i-color-alarm`).
- `shape` — 형태 표기(점선 테두리, 흐린 값, 눈금 숨김, 굵은 테두리, 왼쪽 막대 등).
- `text` — 상태 문구. `{age}`·`{reason}` 은 실제 값으로 치환된다.
- `priority` — 앞에 적힌 상태일수록 먼저다. `invalid` 가 `alarm` 보다 앞이므로, 신호가 아예 없으면 경보보다 "신호 없음" 을 보여 준다.

"manual 을 stale 보다 먼저 보여줘" 같은 요청은 `priority` 배열의 순서만 바꾸면 된다.

## 3-3. 상태는 누가 정하나 — `src/domain/signal.ts`

중요한 규칙이 하나 있다. **상태는 데이터 계층(`src/domain/signal.ts`)이 결정하고, 패널은 받은 상태를 그릴 뿐이다.** "계기가 판단하지 않는다" 는 원칙이다.

`signal.ts` 의 `Signal` 클래스가 하는 일:

1. `candidates(now)` — 지금 성립하는 상태 후보를 모두 모은다. 값이 없으면 `invalid`, 임계를 넘으면 `alarm`, `ttl` 을 넘겼으면 `stale`, 품질이 나쁘면 `degraded`, 수동 보정 중이면 `manual`, 그리고 언제나 `normal`.
2. `state(now)` — 후보 중에서 `states.json` 의 `priority` 순서로 **하나만** 고른다.
3. `snapshot(now)` — 고른 상태의 색 토큰·형태·문구(`{age}`·`{reason}` 치환까지)를 담은 불변 묶음을 만들어 화면으로 내려보낸다.

그래서 상태 규칙을 바꾸고 싶으면 **코드가 아니라 `states.json`·`signals.json` 만 고치면** 모든 화면에 반영된다. 00장의 "상태 검사 표" 가 바로 이 `candidates` 중에서 무엇이 뽑혔는지를 보여 준다.

> **📦 패널이 직접 상태를 판단하면?**
>
> 패널(계기)마다 "값이 440 넘으면 빨갛게" 같은 판단 코드를 넣으면, 임계값을 바꿀 때 패널을 전부 찾아 고쳐야 하고, 패널마다 규칙이 달라져 화면이 서로 안 맞는다. 상태 결정을 `signal.ts` 한 곳으로 모으면, 규칙은 `states.json`·`signals.json` 선언에서 오고 패널은 **받은 상태를 그리기만** 한다. 그래서 "경보 기준을 바꿔 줘" 가 선언 한 줄 수정으로 끝난다.

> **📦 우선순위 없이 여러 상태를 한꺼번에 보여 주면?**
>
> 한 값이 동시에 `stale` 이고 `alarm` 일 수 있다. 둘을 함께 표기하면 화면이 번잡하고, 운용자가 무엇부터 봐야 할지 흐려진다. 그래서 `priority` 로 **하나만** 고른다. 다만 경보 수준 자체는 버리지 않고 스냅샷에 남겨 둬서(`signal.ts` 의 `alertLevel` 보존), 필요할 때 참고할 수 있다. "무엇을 먼저 보여 줄까" 를 선언으로 정하는 것이 이 우선순위다.

## 이 장에서 한 것

- `signals.json` 의 신호 카탈로그(토픽·ttl·`limits`·`limitsBelow`)를 봤다.
- `states.json` 의 6종 상태와 `priority`(색 토큰·형태·문구)를 봤다.
- 상태는 `signal.ts` 가 후보를 모아 우선순위로 하나 고르고, 패널은 그리기만 한다는 원칙을 봤다.
