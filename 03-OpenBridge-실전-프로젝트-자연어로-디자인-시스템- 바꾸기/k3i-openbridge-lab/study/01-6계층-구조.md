# 01. 6계층 구조 — 요청을 어느 층으로 보낼까

자연어 요청이 들어오면 가장 먼저 할 일은 **"이 요청은 어느 층을 바꾸는 일인가"** 를 판단하는 것이다. 층을 맞게 고르면 바꿀 파일이 정해진다. 이 장은 그 판단을 익힌다.

## 1-1. 여섯 층

디자인을 여섯 층으로 나누고, **각 층은 바로 아래 층만 쓴다.** 위 층은 아래 층을 조합할 뿐, 두 단계 아래를 직접 건드리지 않는다.

| 층 | 무엇 | 바꾸는 곳 | 코드 수정? |
|---|---|---|---|
| **View** | 화면 = 레이아웃 + 슬롯별 패널 + 신호 연결 | `design/views/*.json` | 아니오 |
| **Layout** | 슬롯 배치 (grid areas) | `design/layouts.json` | 아니오 |
| **Block** | 패널 종류 / 상태 표현 규칙 | `design/panels.json`, `design/states.json` | 새 패널·새 형태일 때만 |
| **Instrument** | 계기 (나침반·타각계·수치) | OpenBridge 제공 — **고치지 않고 조합만** | 새 패널에서 import |
| **Primitive** | 버튼·토글·배지 | OpenBridge 제공 — **고치지 않음** | — |
| **Token** | 색·간격·글꼴 | `design/tokens.json` | 아니오 |
| (데이터) | 신호 카탈로그·임계값·ttl | `design/signals.json` | 아니오 |

위 넷(View·Layout·Block·Token)은 대부분 **JSON 수정만으로** 끝난다. Instrument·Primitive 는 OpenBridge 가 주는 것이라 손대지 않는다.

## 1-2. "각 층은 바로 아래만 쓴다" 는 무슨 뜻인가

- View 는 Layout(슬롯 배치)과 Block(패널)을 **조합**한다. View 안에서 색(Token)을 직접 정하지 않는다. 색은 Block 이 상태 규칙으로, 그 상태는 Token 을 가리켜 쓴다.
- Block(패널)은 Instrument 를 조합하고 Token 을 쓴다. 패널이 OpenBridge 원본 변수를 직접 쓰지 않고 **Token 층을 거친다**(02장).
- 이렇게 층을 지키면, 한 곳을 바꿔도 영향 범위가 그 층 안으로 묶인다. 색을 바꾸고 싶으면 Token 만, 화면 배치를 바꾸고 싶으면 Layout·View 만 손대면 된다.

## 1-3. 요청을 층으로 분류하기

실제 요청을 어느 파일로 보내는지 본다(프로젝트 작업 규칙 `CLAUDE.md` 의 표와 같다).

| 자연어 요청 | 어느 층 | 바꾸는 파일·키 |
|---|---|---|
| "야간에 경보색을 더 어둡게" | Token | `tokens.json` 의 경보색 팔레트 |
| "stale 문구를 '갱신 끊김'으로", "manual 을 stale 보다 먼저 보여줘" | Block | `states.json` 의 `text`·`priority` |
| "배기온도 경보를 440도로" | 데이터 | `signals.json` 의 `limits` |
| "개요 화면 오른쪽에 칸 하나 더" | Layout + View | `layouts.json` + `views/overview.json` |
| "연료 소모량 패널 추가" | 데이터 + View | `signals.json` 신호 추가 + `views/*.json` 슬롯 연결 |
| "추진기 방위 계기 패널 새로 만들기" | Block (새 패널) | 새 패널 코드 + `panels.json` (04장) |

대부분은 JSON 한두 곳을 고쳐 끝난다. **"패널을 새로 만든다"** 처럼 없던 종류를 더할 때만 코드를 건드린다(04장).

## 1-4. 판단 순서

1. 요청이 **무엇을 바꾸려는가** 를 한 문장으로 적는다(색? 임계값? 배치? 문구? 새 패널?).
2. 위 표로 층을 고른다.
3. **어떤 파일의 어떤 키를 바꿀지 먼저 한 줄로 말한다.** 이것을 말하고 나서 수정에 들어간다(막연히 고치지 않는다).

> **📦 층을 안 나누고 한 파일에 다 넣으면?**
>
> 색·임계값·배치·패널을 한 곳에 몰아 두면, "야간 경보색만 바꿔 줘" 같은 작은 요청에도 전체를 헤집어야 하고, 한 곳을 고치다 엉뚱한 화면이 틀어진다. 층을 나눠 두면 바꿀 파일이 요청마다 한둘로 좁혀진다. 영향이 그 층 안에 묶이니, 고치기도 되돌리기도 쉽다.

> **📦 위 층이 두 단계 아래를 바로 쓰면?**
>
> 예를 들어 패널(Block)이 OpenBridge 원본 색 변수를 직접 쓰면, 나중에 OpenBridge 버전이 바뀌어 변수 이름이 달라졌을 때 모든 패널을 찾아 고쳐야 한다. 그래서 패널은 반드시 Token 층(`var(--k3i-*)`)을 거쳐 쓴다. "바로 아래만 쓴다" 는 규칙은 이렇게 **바뀔 때 고칠 곳을 한 층으로 모으는** 장치다.

## 이 장에서 한 것

- 여섯 층(View·Layout·Block·Instrument·Primitive·Token)과 (데이터) 층을 봤다.
- "각 층은 바로 아래만 쓴다" 가 영향 범위를 묶는다는 것을 봤다.
- 자연어 요청을 층으로 분류해 바꿀 파일을 고르는 법을 익혔다.

다음 **02장**에서는 가장 아래 Token 층부터 본다. 색이 어떻게 OpenBridge 변수를 가리키는지, 팔레트가 어떻게 따라오는지 다룬다.
